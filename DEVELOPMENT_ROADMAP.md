# 🛠️ Mega Pixel World — ПОЭТАПНЫЙ ПЛАН РАЗРАБОТКИ

> Отдельный производственный документ проекта.
>
> **README.md отвечает на вопрос «что представляет собой игра и как устроены её системы».**
> **Этот документ отвечает на вопрос «в каком порядке это всё создавать, что является зависимостью, что проверять и когда переходить дальше».**
>
> Главный принцип: сначала строится маленький, полностью рабочий мир, затем его сложность наращивается слоями. Нельзя начинать с огромного MMORPG-backend, полноценного AI или тысяч контента, пока не доказано, что базовая симуляция мира работает локально в браузере.

---

# 0. Архитектурное решение до начала разработки

## 0.1. Главная цель

Игру необходимо сделать так, чтобы базовый игровой цикл работал:

- в обычном браузере;
- локально;
- на статическом hosting;
- на GitHub Pages;
- без базы данных;
- без постоянного backend;
- без обязательного AI;
- без дорогой инфраструктуры.

Online, LAN и локальный AI должны подключаться поверх уже работающего Game Core.

## 0.2. Порядок режимов

```text
OFFLINE
  ↓
LOCAL SAVE
  ↓
LAN
  ↓
ONLINE ADAPTER
  ↓
OPTIONAL CLOUD INFRASTRUCTURE
```

Нельзя делать наоборот.

## 0.3. Критическая граница архитектуры

Game Core не должен импортировать WebSocket, SQL, HTTP-auth, LLM SDK или серверные библиотеки.

Game Core должен уметь:

```text
seed → generate → simulate → modify → save → load
```

а сетевой слой лишь передаёт необходимые изменения.

# 2. Как читать каждый этап

Каждый этап имеет четыре обязательных уровня:

### A. Foundation
Что должно существовать технически.

### B. Gameplay
Что уже может делать игрок.

### C. Simulation
Какие процессы происходят без игрока.

### D. Definition of Done
Какие проверки доказывают, что этап действительно закончен.

Запрещено считать этап завершённым только потому, что экран или кнопка уже существует.

# 3. ЭТАП 01 — FOUNDATION

## Цель

Создать минимальный проект, который запускается одной командой и отображает пустой игровой мир.

## Сделать

1. Создать Git-репозиторий.
2. Создать Vite + TypeScript проект.
3. Подключить выбранный 2D runtime.
4. Разделить код на:

```text
src/
  core/
  world/
  entities/
  simulation/
  rendering/
  ui/
  data/
  save/
  network/
  ai/
  editor/
  tests/
```

5. Настроить ESLint.
6. Настроить formatter.
7. Настроить unit-test runner.
8. Настроить production build.
9. Проверить GitHub Pages.
10. Проверить локальный запуск.

## Первые экраны

- загрузка;
- главное меню;
- новый мир;
- загрузка мира;
- настройки;
- debug screen.

## Definition of Done

- `npm install && npm run dev` запускает игру;
- `npm run build` создаёт статический build;
- build открывается на GitHub Pages;
- проект не требует backend;
- ошибки TypeScript отсутствуют;
- существует минимальный тест Game Core.

# 50. Правило перехода к следующему этапу

Переходить дальше можно только когда выполнены одновременно три условия:

### Техническое

Система работает без критических ошибок.

### Игровое

Система реально используется в игровом цикле.

### Системное

Система не ломает уже существующие сохранения и симуляцию.

Если третье условие не выполнено — этап не считается законченным.

# 52. Практический режим разработки

Для каждого крупного этапа сначала создаётся вертикальный slice.

Пример для экономики:

```text
1 city
+ 3 shops
+ 10 items
+ 5 NPC merchants
+ 1 resource
```

Сначала доказывается, что экономика работает на маленьком примере.

После этого система обобщается на весь мир.

Такой же принцип применяется к:

- расам;
- семьям;
- бою;
- подземельям;
- религиям;
- строительству;
- событиям.

# 53. Итоговая философия этапов

Проект должен расти не так:

```text
огромный мир → тысячи функций → попытка заставить всё работать
```

а так:

```text
маленький рабочий мир
      ↓
живая симуляция
      ↓
одна жизнь персонажа
      ↓
множество систем
      ↓
множество жизней
      ↓
история мира
      ↓
огромный мир
```

Главная цель — не количество экранов, рас или предметов.

Главная цель — чтобы игрок открыл сохранение через неделю, родился снова и почувствовал:

> **«Этот мир продолжал жить без меня».**
